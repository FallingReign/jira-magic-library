# Upgrade to JML 3.0

Version 3.0 fixes issue creation from pasted JSON, YAML and CSV. Applications should continue passing the original text to `issues.create({ data, format })`. JML owns parsing and field conversion.

## F1: Time Tracking

All of these YAML forms set a two-hour original estimate:

```yaml
Time Tracking: 2h
```

```yaml
Time Tracking: "2h"
```

```yaml
Time Tracking:
  originalEstimate: "2h"
  remainingEstimate: "1h"
```

`Original Estimate: 2h` and `Remaining Estimate: 1h` also work as top-level fields. JSON accepts the same scalar or nested object values. JML sends Jira an object such as `{"originalEstimate":"2h"}`. Unknown nested keys are rejected with their names in the error.

## F2: Optional fields

During **creation**, an omitted field, `null`, `undefined`, `""`, or whitespace-only string is treated as blank. Blank optional fields are omitted from the Jira request in every input format. This includes Sprint and empty time-tracking objects. Zero and `false` are kept.

```json
{
  "Project": "TEST",
  "Issue Type": "Task",
  "Summary": "Example",
  "Time Tracking": { "originalEstimate": "2h" },
  "Sprint": ""
}
```

Blank required fields fail before submission, unless Jira metadata says the field has a default. This is creation behavior; it does not redefine how an update clears an existing field.

## F3: Pasted descriptions

JML supports `<<<` and `>>>` blocks in JSON, YAML and CSV. The markers delimit a whole field value. Put the opening marker before a newline and the closing marker on its own line (a trailing JSON comma/brace is allowed).

This is JML's extended JSON input, processed before ordinary JSON parsing:

```text
{
  "Project": "TEST",
  "Issue Type": "Task",
  "Summary": "Example",
  "Time Tracking": { "originalEstimate": "2h" },
  "Sprint": "",
  "Description": <<<
The user said "it's broken".
Path: C:\work\file.txt

Keep this blank line and the original text.
>>>
}
```

YAML uses the same block:

```text
Description: <<<
The user said "it's broken".
Path: C:\work\file.txt
>>>
```

Quoted wrappers (`"<<<` ... `>>>"`) are also supported. Block contents are literal: quotes, backslashes, Unicode, indentation, blank lines and line endings are preserved. The newline immediately after `<<<` and the newline introducing `>>>` are delimiters. An unmatched opening marker produces an error with its line and column.

A standalone closing marker ends a block. If the description itself contains that marker on its own line, build a JavaScript object and serialize it with `JSON.stringify` instead.

On Jira Server/Data Center, descriptions are submitted as strings. Jira Cloud still uses the existing ADF conversion; Cloud formatting is not a byte-for-byte text storage contract.

## F4: Standard parsing and compatibility mode

Valid JSON now follows ordinary JSON escaping rules. For example, `"Line 1\nLine 2"` contains a newline; `"C:\\work"` contains one backslash. JML no longer doubles already escaped content, trims free text, or rewrites Unicode in field values. Field names still receive whitespace and Unicode normalization. Duplicate names after normalization are rejected.

The default is `preprocessQuotes: false`. Prefer literal blocks for text pasted by people and `JSON.stringify` for data generated by an application.

Legacy quote repair is available explicitly:

```js
const result = await jml.issues.create({
  data: legacyTemplate,
  format: 'yaml',
  preprocessQuotes: true,
});
```

It can also be set on the JML configuration. A per-input setting overrides that configuration. Repair runs only after ordinary parsing fails; valid strings and literal blocks keep their standard meaning. Repair is best effort and cannot infer every malformed template's intent.

## F5: Preview and validation

`issues.preview()` prepares fields without submitting an issue. Check `valid` before displaying or using its payload. Failed preparation returns `valid: false`, an empty payload and an explanation in `warnings`.

`issues.create(input, { validate: true })` never submits issues or uploads attachments, including raw input, arrays, hierarchy batches and retries. Lookup reads and metadata caching may still occur.

Single-object validation retains the existing `DRY-RUN` Issue-shaped response. Array and parsed-input validation now returns `BulkValidationResult`:

```js
const checked = await jml.issues.create({ data, format: 'json' }, { validate: true });
if (checked.validation && checked.valid) {
  // Review checked.results[index].payload.
  // Call create again without validate only when creation is intended.
}
```

Each row includes `index`, `valid`, `payload` or `error`, and `dependencies`. Local parent references are reported as pending dependencies; validation does not invent parent issue keys. Use this bulk validation result for hierarchy batches. It contains no creation-success counts or stored manifest. Retry validation checks failed rows from the existing manifest without updating that manifest.

## SHGJiraTools handoff

1. **A1 — Dependency:** Update the Git dependency from `#v2.2.0` to `#v3.0.0` and refresh its lockfile.
2. **A2 — Input:** Keep advanced and deprecated handlers passing `{ data, format }` verbatim. Normalize only the format alias `yml` to `yaml`.
3. **A3 — Templates:** Check existing templates for malformed quoted text that relied on automatic repair. Move pasted descriptions to literal blocks. Enable compatibility mode only where migration requires it.
4. **A4 — Validation UI:** If the app consumes validation or preview, handle the new bulk validation result and `preview.valid`. Do not treat a validation result as a created issue.
5. **A5 — Acceptance:** Test both YAML estimate quote styles, nested estimates, blank JSON Sprint, and descriptions containing quotes, paths, Unicode and newlines through the actual application. Run the application's test suite, then follow its deployment process and verify the running library version.

The library release does not update or deploy SHGJiraTools.
